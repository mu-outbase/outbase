# 天気の未取得表示とカレンダー入力の維持

利用者から「更新しても予報が出ない」「入力窓がまだ勝手に閉じる」と報告。スワイプ修正だけでは不足していた。

## カレンダーが閉じる経路

天気のapp-open・focus等の非同期取得後に、現在の画面を無条件で再マウントしていた。加えて活動詳細ラッパーが活動以外の画面にも読み込み表示を書き込み、ベースとdirect-fixもカレンダーiframeを作り直していた。天気更新後の描画はHOMEだけにし、活動用の仮表示を活動画面に限定、同一カレンダーURIのiframeを保持する。月や条件を明示変更した場合の切り替えは維持する。

PWA更新のcontrollerchangeでもフォームが消えるため、予定・ToDo入力中および予定編集フォーム中は再読み込みを延期する。カレンダーから同一origin・現在iframeの閉じ通知を受け、保存・明示的な閉じ操作が済んでから一度だけ切り替える。初回PWA登録で再読み込みしない動作は維持。予定・ToDoの窓は背景タップやスワイプでも閉じず、保存・明示的な閉じボタンを使用する。

## 天気

キャッシュがない対象にnullを返してHOMEが永続loadingを作っていた。場所未設定・見つからない場所・通信失敗を区別し、未取得の時刻を取得成功時刻にしない。部分成功は部分成功と表示し、キャッシュがある失敗では実際の前回データと時刻を維持して古い予報と明示する。詳細画面も未取得から雨や風の判断を合成しない。null座標を0,0と解釈しない。空の天気応答は成功キャッシュにしない。

予定の場所がキャンプ場名の場合、市区町村検索で見つからなければ既存のPOI検索機能を利用する。新しい天気APIは追加しない。場所未設定ではタイトルから地点を推測せず、予定の場所欄を入力する案内を表示する。提供画像の予定は場所未設定だった。

## 確認

- Pixel 7で天気応答を保留してカレンダーへ入力後、応答完了・汎用再描画・focus更新を実施。iframeとformの同一DOM、タイトル・メモ維持を確認。
- 場所未設定の案内、場所指定後の予報成功、通信失敗時の前回値・時刻保持、空キャッシュ失敗でloadingが終わることを確認（予報応答は制御fixture）。既存取得先への実通信も200・16日分を確認。一度は503があり、端末側の原因とは断定しない。
- 実際にSWを更新し、入力中に再読み込みせず、保存後に一度だけ再読み込みして予定が残ることを確認。
- 天気状態の単体5件、資材整合、HTMLインラインの構文、カレンダータッチ操作、既存連携とGate2 26/26、モバイル戻る操作・横はみ出し、初回登録と連続更新・記録保持・オフライン起動が成功。

起動・shell・domain・legacy・天気サービス・iframeとカレンダーJSの実際のURLを更新してSWに揃えた。利用者の端末を操作した検証ではない。
